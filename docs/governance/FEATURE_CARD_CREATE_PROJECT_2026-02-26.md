# Feature Card: Создать Проект

Статус: historical feature card; current runtime contract uses `Project`, `/projects/*`, `ProjectNewPage`, and `ProjectSite`.

## 1) Ценность

- Пользователь должен создавать новую сущность `Проект`.
- Цель: понятный входной сценарий создания и дальнейшего управления проектом.

## 2) Scope (итерация 1, согласовано)

- Реализовать только функцию создания проекта (UI + create-логика).
- Переименовать UI-entrypoint в `+ Создать проект`.
- Согласовать навигационную роль `Рабочая область` и action-роль `Создать проект`.
- Зафиксировать терминологию (RU-only): используем `Проект`.
- Параметры формы итерации 1:
  - `Название проекта` — необязательно;
  - `Домены` — обязательно, минимум 1;
  - если `Название проекта` пустое, подставляем авто-имя из домена.

## 3) Out of Scope (пока не делаем)

- Скан/краулинг, расписания, уведомления, сравнение прогонов.
- Сложная аналитика/отчеты по изменениям страниц.
- Миграции БД с тотальным rename старых сущностей без отдельного RFC.

## 4) Reuse First Check

- Базовый routing/layout уже есть (`AppLayout`, `ProjectNewPage`, `Button`, `SectionHeaderRow`).
- Для UX-слоя использовать существующие паттерны из:
  - `REUSE_INDEX.md`
  - `docs/ui/UI_TAXONOMY_MATRIX.md`
  - `PATTERNS.md`

## 5) Матрица влияния

1. UI: Да.
  Комментарий: тексты, кнопки, названия блоков, возможно заголовки страниц.
2. API: Возможно.
  Комментарий: зависит от решения — оставить текущие endpoints или добавить alias-слой.
3. DB: Нет (для первой итерации).
4. Perf: Низкое влияние.
  Комментарий: не увеличивать число запросов.
5. Security: Нет изменений ролей/permissions (ожидаемо).
6. Sync: Низкое влияние.
  Комментарий: не ломать существующие multi-user сценарии.
7. Audit/Event: Проверить.
  Комментарий: если появятся новые действия, нужен аудит/события по правилам.

## 6) Риски

- Терминологический drift (`профиль` и `проект` одновременно в разных местах) — закрыто в legacy cleanup.
- Регресс навигации из-за переименований route labels.
- Потеря обратной совместимости, если затронем API/модели без переходного слоя.

## 6.1) Навигация `Рабочая область` vs `+ Создать проект`

Нужно разделить:

- `Рабочая область` = раздел (где пользователь находится).
- `+ Создать проект` = действие (что пользователь делает).

Варианты:

1. Вариант A (рекомендуется для старта)
- В sidebar оставляем `Рабочая область`.
- В sidebar оставляем `+ Создать проект` как быстрый shortcut.
- На странице `Рабочая область` дублируем главный CTA `+ Создать проект`.

2. Вариант B (минималистичный)
- В sidebar только `Рабочая область`.
- `+ Создать проект` только на странице `Рабочая область`.

3. Вариант C (не рекомендован)
- Убрать `Рабочая область`, оставить action-кнопку как главный вход.
- Риск: ломается логика навигации разделов.

Рекомендация: начать с Варианта A, потом упростить до B по факту использования.

## 7) Definition of Done (для итерации 1)

- В UI согласован и внедрен термин `Проект` в согласованном scope.
- Entrypoint `+ Создать проект` работает без регрессий текущего сценария создания.
- Frontend build проходит.
- Обновлены релевантные `.md` (TODO/REUSE/при необходимости taxonomy).
- Скан/прогоны/сравнение не затронуты (явно вне scope).

## 8) Что нужно согласовать перед внедрением

1. Глубина переименования:
  - `A` только UI-термины + create-flow;
  - `B` UI + route aliases;
  - `C` UI + API aliases (без DB rename).
2. Обратная совместимость:
  - сохраняем текущие пути/контракты как есть на первую итерацию;
  - новые названия добавляем поверх, без ломки старого.
3. Точка входа:
  - утвердить вариант A/B по связи `Рабочая область` и `+ Создать проект`.
4. Доменный ввод:
  - подтверждено: принимаем и корневой домен, и URL;
  - нормализуем до домена (`example.com`, `sub.example.com`), путь/схему не храним в списке доменов.

## 9) Рекомендация по внедрению (итерация 1)

- Начать с варианта `A` (UI-first, no-regression).
- Реализовать только создание проекта.
- После стабилизации creation-flow отдельно обсудить скан/прогоны/сравнение как следующую фичу.

## 10) Статус согласований (2026-02-26)

- Навигация: выбран вариант A.
- Имена/язык: RU-only, термин `Проект`.
- Форма:
  - доменов `>=1`;
  - имя опционально;
  - авто-имя при пустом имени.
- `Рабочая область`: используется как верхний уровень для проектов (список проектов + CTA `+ Создать проект`).

## 11) Реализация (итерация 1, update)

- `Рабочая область` переведена в project-hub:
  - список проектов,
  - поиск проектов,
  - быстрые действия `Открыть`/`Удалить` (с confirm).
- Форма создания проекта работает по правилам итерации 1 (create-only).
- Отображение доменов разделено по контекстам:
  - в списках (`Workspace`/`SidebarLeft`) используется compact-summary `first-domain +N`;
  - в карточке проекта (`/projects/:id`) показывается выбранный `ProjectSite` и его технический allowlist/scope.
