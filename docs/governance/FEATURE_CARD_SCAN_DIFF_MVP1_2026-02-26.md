# Feature Card: Scan & Diff MVP-1

Статус: draft

Реализация: `docs/governance/IMPLEMENTATION_PLAN_SCAN_DIFF_MVP1_2026-02-26.md`

## 1) Цель MVP-1

- Запустить базовый сбор данных по страницам проекта без сложных авторизационных контекстов.
- Подготовить данные так, чтобы позже без переделок добавить 2 режима сравнения:
  - `Визуальный` (скриншот vs скриншот),
  - `Код` (diff HTML/DOM/ресурсов).

## 2) Пилотные сайты

- Простой пилот: `https://books.toscrape.com/`
- Авторизационный пилот (следующая итерация): `https://quotes.toscrape.com/login`
- Боевой ориентир после релиза: `https://www.bitrix24.by/`

## 3) Scope MVP-1 (включено)

1. Базовый обход страниц проекта (без auth-контекстов).
  - первый прогон запускается вручную;
  - далее — режим сервиса по расписанию (с рекомендацией запускать в непиковые часы).
2. Сбор по каждой странице:
- URL, status, content-type, размер;
- исходный HTML;
- финальный DOM после рендера;
- screenshot фиксированного viewport;
- мета-данные SEO (`title`, `description`, canonical, robots, og, h1);
- ссылки/ресурсы (css/js/img) + коды ответа;
- битые ссылки/ресурсы (404/ошибки).
3. Подготовка к diff:
- hash-артефакты (HTML/DOM/resources/meta/text);
- минимальная нормализация шума (timestamp/nonce-подобные паттерны).

## 4) Out of Scope MVP-1

- Авторизация/подавторизации/персоны (контексты).
- Сравнение между доменами.
- Полноценный UI двух окон `Визуальный/Код` (только подготовка данных).
- Получение `PHP source` (не требуется и технически нецелесообразно для веб-краулинга).

## 5) Data Contract (черновик)

1. `page_snapshot`
- `project_id`, `run_id`, `url`, `status_code`, `final_url`, `fetched_at`
- `html_blob_ref`, `dom_blob_ref`, `screenshot_blob_ref`
- `meta_json`, `links_json`, `resources_json`
- `hash_html`, `hash_dom`, `hash_meta`, `hash_resources`

2. `page_diff_index` (для быстрого списка изменений)
- `project_id`, `run_prev_id`, `run_last_id`, `url`
- `changed_visual`, `changed_code`, `changed_meta`, `changed_links`, `changed_resources`
- `severity`, `summary`

3. `project_stats_history` (permanent агрегаты для отчетов)
- хранится независимо от жизненного цикла проекта;
- содержит исторические срезы KPI/impact по run (`day/week/month` rollups);
- используется для будущего экспорта (`месяц/квартал/полугодие/год`).

4. `project_deletion_log` (audit удаления проекта)
- `project_id`, `deleted_by`, `deleted_at`, `reason`;
- `last_run_id`, `previous_run_id`, `raw_artifacts_pruned`;
- служит трассировкой delete-flow и подтверждением retention-политики.

## 5.1 Retention Policy (утверждено)

- Raw snapshot-артефакты (`html/dom/screenshot/resources/links`) храним только для `latest + previous` run на проект.
- Для более старых run сохраняются только легкие агрегаты/индексы для отчетности.
- При удалении проекта run-raw данные подлежат очистке по retention-политике, но статистические агрегаты (`project_stats_history`) остаются перманентно.

## 6) Узкие места и guardrails

1. Нагрузка:
- лимит concurrency и batch-size;
- дедуп по URL и hash;
- хранить тяжелые артефакты как blob/ref, а не в основных таблицах.

2. Ложные изменения:
- фильтрация шумовых полей;
- сравнение по нормализованным версиям.

3. Безопасность:
- не хранить чувствительные cookie/токены в открытом виде;
- cookie/state данные хранить только в маскированном/хэшированном виде и только если это нужно для диагностики;
- соблюдать robots/ограничения доступа.

## 7) Следующая итерация (MVP-2)

- Auth contexts (`Гость`, `Авторизован`, `Авторизован + параметр`).
- UI переключатель режимов `Визуальный / Код` с diff-подсветкой.

## 8) Project Page Design (подготовлено)

- `ProjectDashboardPage` переведен из заглушки в проектный skeleton:
  - карточка проекта (имя, домены, базовые действия),
  - карточка `Скан и данные` (без diff-блока на этом шаге),
  - карточка последнего прогона (статус/время/объем).
- блок `Расписание` выведен в UI-прототип (enabled/frequency/window) до подключения persistence API.
- добавлен вкладочный каркас проекта: `Сводка | Расписание | Структура | История` (прототип под дальнейшее подключение API).
- `SidebarLeft` и `Рабочая область` используют summary-представление (`runs_total` + `last_run`) для мягкой статусной индикации проектов.
- `runs.start` переведен с single-page запроса на базовый multi-page обход (BFS) в пределах домена проекта и лимита `max_pages`.
- Сравнение (`Визуальный/Код`) вынесено в отдельный следующий шаг с расширенным layout.
- Это UI-контракт под MVP-1 без изменения текущей бизнес-логики.
