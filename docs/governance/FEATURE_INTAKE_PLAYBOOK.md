# Feature Intake Playbook

Цель: добавлять новые фичи предсказуемо, без регрессий, с реюзом существующих механик и контролем нагрузки.

## 1) Когда использовать

- Для любой новой фичи или заметной доработки существующей.
- Не применяем только для микро-правок текста/стилей без логики.

## 2) Что заполняем перед началом

1. `Название фичи`
2. `Пользовательская ценность` (какую проблему решает)
3. `Границы` (что входим в scope, что не входим)
4. `Риски` (что можем сломать)
5. `Критерий готовности` (как поймем, что фича закончена)

## 3) Reuse First (обязательно)

Перед кодом проверяем:

1. `REUSE_INDEX.md` — есть ли готовый reusable.
2. `docs/ui/UI_TAXONOMY_MATRIX.md` — есть ли каноничный UI-паттерн.
3. `PATTERNS.md` — есть ли действующий контракт поведения.

Правило: сначала `extend existing`, потом `create new`.

## 4) Матрица влияния фичи (просто и обязательно)

Для каждой зоны ставим `Да/Нет` и короткий комментарий:

1. `UI` — новые экраны/состояния/адаптивность.
2. `API` — новые/измененные endpoints и контракты.
3. `DB` — миграции, индексы, новые поля.
4. `Perf` — изменение числа запросов/рендеров/памяти.
5. `Security` — permissions, роли, sensitive данные.
6. `Sync` — многопользовательские гонки/консистентность.
7. `Audit/Event` — логирование действий и события в Event Center.

Зачем: это быстрый способ заранее увидеть риск и не забыть важное.

## 5) Feature Flag (когда нужен)

Feature flag нужен, если фича:

1. меняет важную бизнес-логику;
2. влияет на данные или права;
3. может заметно повлиять на нагрузку;
4. затрагивает много пользователей сразу.

Если фича локальная и низкорисковая — flag не обязателен.

## 6) PR-шаблон (зачем и как)

PR-шаблон — это короткая форма, которую заполняем в каждом PR.

Зачем:

1. Ревью быстрее.
2. Меньше “забытых” проверок.
3. Видно, что именно проверено.

Что обязательно в PR:

1. `Что было` и `что стало`.
2. `Скоуп` (файлы/модули).
3. `Матрица влияния` (UI/API/DB/Perf/Security/Sync).
4. `Проверки` (build/tests/smoke).
5. `Риски и откат` (если что-то пойдет не так).
6. `Документация` (какие `.md` обновлены).

## 7) UX-тексты и локализация

Текущая политика проекта: только русский язык.

Что это означает:

1. Все новые тексты интерфейса пишем на русском.
2. Используем единые термины по всему UI (например, `Проект`, а не смесь `Проект/Профиль`).
3. Ошибки пишем простыми фразами: что случилось и что делать пользователю.

## 8) Минимальная валидация перед merge

1. Frontend: `npm run -s build`
2. Backend: таргетные тесты по измененной зоне
3. Smoke: короткий ручной сценарий по основной функции
4. Проверка, что не нарушили server-load и multi-user sync

## 9) Доки после merge (обязательно)

1. `TODO.md` — статус/результат.
2. `REUSE_INDEX.md` — новый реюз или расширение существующего.
3. При необходимости: `PATTERNS.md`, `docs/ui/*`, `docs/audits/*`.

## 10) Контекст фичи (чтобы не потерять логику)

Для каждой фичи заводим компактную карточку:

1. `Решение и почему`
2. `Ограничения`
3. `Открытые вопросы`
4. `Что отложили на потом`

Это снижает риск “забыть договоренности” через 1-2 недели.
